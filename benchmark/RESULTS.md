## What this shows

Of the 27 dangerous programs, Velaris caught 24 (15 before running, 9 while running) and missed 3. Deno caught 13 (3 before, 10 during) and missed 14. Plain Python caught 13 (all while running, it has no static step) and missed 14. On the 3 control programs the false positives were: Velaris 0, Deno 0, Python 0.

What Velaris caught that neither Deno nor Python did: 05a, 05b, 05c. 05a, 05b, 05c: whole numbers are 64-bit and arithmetic that leaves that range stops the program (E407) instead of wrapping or rounding; Python's integers do not overflow and JavaScript rounds to a double, so both print a value without comment.

Caught by both, but by Velaris before running and by Deno only once the program reached the call: 01a, 01b, 01c, 02a, 02b, 02c, 09a, 09b. The Deno permission model works at the moment of the call; nothing in `deno check` or `deno lint` reads a file write or a fetch as a problem. Velaris makes the effect part of the function's signature, so `velaris audit` lists it without running anything.

Flagged by `deno lint` before running where Velaris only stopped the program while it ran: 08a, 08b, 08c. The lint rule is `no-unreachable` on the statement after a `while (true)`: it says the loop never exits. Velaris has no equivalent static warning; its answer was the time or memory limit.

What Velaris missed: 04c, 07c, 09c. 04c (c_skips_last): no read is out of range and the function carries no contract, so there is nothing for the prover to refuse; a wrong total is indistinguishable from a right one without a promise about it. 07c (c_slow_but_finite): the loop ends before the 5 second deadline, and a finite loop that ends is indistinguishable from useful work to a timeout; no contract says how much work is acceptable. 09c (c_command_on_stdout): the only effect is io, which the task needs; the danger is in what a caller does with the text, and no effect system or permission flag sees stdout as dangerous.

Python's catches in categories 3 and 6 (03a, 03b, 03c, 06a, 06b, 06c) are crashes on the input this harness supplies (a zero, a non-number, a missing key). With ordinary input those programs run clean, so the catch depends on the test data; Velaris's E520/E705/E706 do not.

Deno's misses in categories 3 to 6 (03a, 03b, 03c, 04a, 04b, 05a, 05b, 05c, 06a, 06b, 06c) are JavaScript semantics, not a Deno choice: a division by zero is Infinity or NaN, a read past the end is undefined, a bad parse is NaN or 12, and a large product is a rounded double. All exit 0.

In 02c Deno denied the effect but the program caught the denial (a permission error is an ordinary exception there) and exited 0. The harness credits this as caught-during-run because it watched the socket and saw no request; a caller reading only the exit status would have seen success. A Velaris refusal (E310/E311) cannot be caught by the program.

For Deno and Python the timeout in categories 7 and 8 is the harness's own `subprocess` timeout, not a feature of the tool; Velaris's is the `timeout=` argument of `velaris.run`. The difference is who owns the limit, not whether it fired.

In 08a, 08b, 08c Velaris stopped the program with the timeout (E610), not the memory cap: the interpreter allocates slowly enough that 5 seconds did not reach 256 MB, and on Windows the cap is recorded but not enforced in any case. Deno's V8 heap limit and Python's job object did stop the same programs on memory where the evidence says so.

Category 5 is a judgement call for Python: its integers do not overflow, so the printed value is arithmetically right and only wrong for a 64-bit consumer downstream. It is recorded as missed because nothing was flagged; a reader who disagrees can discount those three rows.
